# Issue #13：大历史 session 的恢复性能回退

## 原因与复现

1.5.0 为修复 Vim/htop 的 normal/alternate screen 恢复，将 scrollback、两种屏幕及终端状态分别捕获。但新流程引入了以下问题：

1. 每个有历史的 pane 都执行 `capture-pane -S- -E-1` 和 `capture-pane -S- -E0`。第二条命令只是用于判断历史与首屏行之间的软折行，却再次传输整份历史。issue 中每个 pane 约有 4.6～4.9 万行历史，这一开销随 pane 数量增长。
2. 在收到全部捕获响应后，才发送结束状态查询。大历史的网络传输时间被纳入状态校验区间；校验又比较整个 PaneState，包括光标、history size 等会随普通输出变化的字段。正常日志输出或界面刷新都可能导致失败，并重新捕获最多三次。
3. 所有 pane 同时入队，命令的超时从发送时开始计时。后面的响应尚在前面的大响应之后等待，就可能触发 30 秒超时。超时只结束本地等待，不会取消已发送给 tmux 的命令；原实现重试会继续增加积压。
4. 等待全部 pane 捕获完成才发出 pane-add 和 layout-change，导致当前 window 也被后台 window 阻塞。预捕获失败后，pane 启动还会再次发起捕获。
5. 退出时发送 detach 后立即移除输出拦截器。积压的 Control Mode 响应仍在传输，于是 `%begin`、`%end`、`%exit` 等协议文本进入原终端。

单纯延长超时、删除历史或退回旧的双屏幕恢复逻辑均不能解决这些根因。

## 修复设计

- 完整历史每个 pane 只读取一次。边界检查改为 `capture-pane -peJN -S-1 -E0`，只读取最后一个历史物理行与屏幕首行；两行之间有没有换行即可判断是否软折行。保留空行、尾部空格、颜色与历史完整性，不增加历史截断。
- 捕获命令与结束状态查询通过 gateway 的批量接口在同一次传输写入。每条命令仍独立成行，拥有自己的响应槽；不用分号序列，避免某条命令错误后跳过后续命令、破坏响应匹配。
- 只对尺寸、normal/alternate 切换以及历史从无到有/从有到无的变化进行有界重试。使用结束状态恢复光标和模式；普通光标移动与 history size 增长不再导致重传。捕获错误或超时不进行整份历史重试。
- 所有捕获入口共用串行队列，同一 pane 的并发请求共用一次捕获。优先恢复 tmux 当前 window；每个 window 的全部 pane 就绪后立即发布 layout，让 UI 提前挂载，同时避免对未完成的 split 提前创建视图。初始 window 元数据事件不再触发提前切换。
- 预捕获失败由首次 pane 启动消费一次，保留实时输出，避免立即发起第二轮捕获。后续重新挂载仍可抓取新快照。
- controller 销毁时停止后续捕获并取消本地待处理命令。退出 UI 后，拦截器继续丢弃协议数据，直到收到 `-CC` 的 DCS 结束符 `ESC \\`。支持结束符跨包，以及结束符后同包的 shell 提示符；底层 session 关闭也会释放拦截器。同一终端再次 attach 前等待旧拦截器移除，避免快速退出/重新进入时叠加拦截器、将 shell 启动命令写入旧 Control Mode。

## 可重复的基准

```bash
pnpm run test:performance
# 可指定二进制及追加写入 JSONL 的位置：
TMUX_TEST_BINARY=/path/to/tmux VIM_TEST_BINARY=/path/to/vim \
  TMUX_BENCH_OUTPUT=/tmp/snapshot-benchmark.jsonl pnpm run test:performance
```

需要 tmux >= 3.1、Vim。每个测试创建独立临时 server 和 socket，并只清理自身资源，不接触现有 session。缺少二进制时基准命令会失败；普通 `pnpm test` 默认跳过真实 tmux 测试。

场景覆盖：

- 1 个 pane / 1,000 行普通历史；
- 1 个 pane / 1,000 行软折行历史，并逐行对照 tmux 可见屏幕；
- 1 个 pane / 50,000 行普通历史；
- 4 个 window、各 1 个 pane / 各 50,000 行历史；
- 50,000 行历史后持续刷新光标的 pane；
- 50,000 行历史后进入 Vim alternate screen。

统一使用 189×52 的 grid，对真实 Control Mode 数据流施加约 8 MiB/s 的接收延迟，经过生产 gateway、controller、pane session 和真实 headless xterm 渲染。计时不包含准备 tmux 历史的耗时。这不是 Tabby GUI 或真实 SSH 网络耗时的承诺。

每次执行必须满足以下预算，否则测试失败：

- 完整历史读取次数等于 pane 数，防止重复读取和重试风暴；
- 接收字节数 < 实际历史字节数 × 1.15 + 每 pane 32 KiB，容纳状态、屏幕和实时输出；
- 总恢复耗时 < 3 秒 + 理想 8 MiB/s 历史传输时间的三倍，为 CI CPU 差异留出余量；
- 多 window 时，第一个 pane 完成 xterm 渲染的耗时 < 总耗时的 70%，防止全局等待重新出现；
- 历史首尾标记完整，静态场景逐行匹配 tmux 当前屏幕，且没有捕获警告。

同时用普通回归测试验证持续输出不重传、状态查询与捕获一起发送、结构变化重试、命令失败后响应对齐、串行和同 pane 去重、当前 window 优先、UI 提前挂载、超时后不追加历史捕获，以及退出时的协议过滤。

CI 在构建前执行 lint、生产及测试 typecheck、format、单元测试、真实 tmux/Vim/htop 集成测试和性能预算检查；保存每次基准的 JSONL artifact，便于比较耗时趋势。

## 修复前后测量

本机 Linux、Node.js 22.22.3、tmux 3.4；相同历史、grid、8 MiB/s 接收延迟及 headless xterm。以下为单次测量，时间会随机器与调度波动，字节量和完整读取次数为主要回归依据。

| 场景 | 1.5.0 接收字节 | 修复后接收字节 | 首 pane 就绪（前 → 后） | 总恢复时间（前 → 后） |
| --- | ---: | ---: | ---: | ---: |
| 1 pane × 1,000 行 | 233,503 | 120,691 | 65 → 52 ms | 101 → 81 ms |
| 1 pane × 50,000 行 | 11,895,509 | 5,951,697 | 2,023 → 1,043 ms | 2,164 → 1,176 ms |
| 4 pane × 50,000 行 | 47,581,391 | 23,806,143 | 8,173 → 1,041 ms | 8,656 → 4,554 ms |

上述“就绪”指 controller 发布 pane-add，便于与修复前同一指标比较。修复后 4 pane 场景首个 xterm 实际渲染完成为 1,142 ms；修复前基线未单独记录首个渲染完成时间。完整历史读取次数从每 pane 2 次降为 1 次。修复前原代码在三个相同场景均触发基准失败。

修复后持续输出和 Vim 场景也只读取一次完整历史，分别接收 5,953,304 / 5,961,489 字节，总恢复耗时约 1,236 / 1,166 ms。现有真实 Vim 编辑、resize、退出和 htop 颜色测试另外执行，防止性能修复重新破坏 1.5.0 的屏幕恢复正确性。

本次验证：264 项单元测试、5 项真实 tmux/Vim/htop 集成测试、6 项性能基准全部通过；lint 零错误（135 项原有警告）、生产及测试 typecheck、Prettier、Webpack 构建均通过。未进行 Tabby GUI 手工验收。
